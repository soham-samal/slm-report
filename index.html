Recovering Frontier-Level Reliability in a 9B Model Through Tool-Use Fine-Tuning for Financial Question Answering

Soham Samal

In collaboration with the AlphaTax engineering team

October 2026

Abstract

I study whether a 9B open-weight model, given the same retrieved evidence as a frontier model, can close most of the reliability gap on expert-authored tax questions by learning when to call tools rather than by acquiring domain knowledge. I build a supervised fine-tuning corpus from tool-calling sessions graded against CPA-written reference answers. The corpus is de-identified with entity-consistent placeholder tokens and augmented deterministically with calculator calls and search-recovery behavior. I train Qwen3.5-9B with QLoRA on sequences of up to 22.3k tokens; two exact chunked computations (attention and cross-entropy) make these lengths fit in memory. On 42 questions from clients excluded from training, with the model's calculator calls executed, the fine-tuned model answers 41 correctly, the base model 39, and no answer the base model got right is lost. A failure analysis over four base models attributes 54% of failure instances to arithmetic over figures that were already present in the evidence. Separately, I find that offline protocols that do not execute tool calls penalize the behavior the fine-tuning is meant to induce.

1  Problem setting

The task is question answering over a corpus of client tax documents: preparer-copy returns, information returns, and spreadsheet summaries. The model is served behind a Model Context Protocol (MCP) server. The server exposes a hybrid search tool with metadata filters (client folder, tax year) and a deterministic arithmetic tool. Retrieved text is de-identified at index time. Names appear as tokens such as [PERSON_a1b2c3d4], which the model must reproduce verbatim. Answers are limited to two sentences, and every figure must be supported by retrieved evidence.

Frontier models do well on the firm's 152-question benchmark, but deployment constraints favor a small model that can run on infrastructure the firm controls. The question I address is narrower than general capability: with the evidence held fixed, how much of the small-model deficit comes from tool-use behavior (filtering searches correctly, delegating arithmetic, committing to an answer), and how much can a small amount of supervised data recover?

2  Division of work

The AlphaTax engineering team built and operates the ingestion and retrieval pipeline, the vector index, the MCP search server, and the benchmark harness. CPAs at the firm wrote the reference answers and difficulty ratings. I was responsible for the small-model work:

  • the data pipeline: ingestion, quality gates, de-identification, augmentation, and splitting;
  • the base-model sweep;
  • the training recipe and its memory-efficient kernels;
  • the offline and live-tool evaluation harnesses;
  • adding the deterministic calculate tool to the production MCP server;
  • the failure analyses.

3  Data

3.1  Source and quality gates

The source data are recorded sessions of a frontier model answering the benchmark questions through the production search tool. Each record contains every tool call with its arguments, the raw tool responses, and the final answer. I retained a session only if it passed all of the following gates:

  1. it was graded correct with a score of at least 90 of 100;
  2. the question was not flagged as defective by the CPA review;
  3. every tool argument validated against the JSON schema exported from the running MCP server;
  4. the folder filter resolved to a known client directory;
  5. there were no tool errors;
  6. every numeric figure in the final answer was either present in a tool response or derivable from present figures by a sum, difference, or halving.

Of 125 sessions with complete retrieval recall, 119 passed. Recorded tool responses were rewritten back into the exact shape the production search API returns, so the training text and the serving text are byte-compatible.

3.2  De-identification

For human review, the recordings had been stored with names restored in place of the de-identification tokens. I re-applied de-identification using entities that are known for each session: client names parsed from file names (including joint filers), business names, and folder names. I then expanded these to orthographic variants, covering name orders, possessives, and the space-collapsed forms produced by the contextualization step. Each entity maps to a token derived from a hash of the entity, [CLASS_h8], so the same entity receives the same token in every document. This preserves the coreference structure the model has to learn. A residual scan flags any session in which a known entity string survives replacement. The pass made 2,975 replacements and left two flags, both benign.

3.3  Augmentation

The recorded sessions contain no calculator use, no recovery from failed searches, and only one fixed client directory. I added these behaviors deterministically, without generating any text with a model:

  • Calculator insertion. When the answer states a figure x that does not appear in the evidence but equals a−b, a+b, a+b+c, or a/2 for figures a, b, c that do appear, I insert a calculate call together with the tool's actual output. This version replaces the original session (58 of 119).
  • Empty-result recovery. For each session I prepend a search that uses a plausible but wrong folder name and returns {"results": []}, followed by the original trajectory (119 sessions).
  • Directory variants. For each session I build a system prompt whose client directory is shuffled and subsampled to between 30% and 100% of its entries, while always including the folders that session needs. This discourages memorizing the directory (119 sessions).

Together these yield 357 examples, with median length 8.8k tokens and maximum 22.3k. I assign folds by GroupKFold(5) over client folders, so a client appears in exactly one fold. Folds 0, 2, and 3 (231 examples) are used for training. Folds 1 and 4 (42 questions from unseen clients) are held out for evaluation.

4  Training

Each example is rendered through the model's own chat template, including the tool definitions. The loss is masked to assistant spans, which contain the tool-call JSON and the final answer. System, user, and tool turns are labeled −100, so the gradient never rewards reproducing retrieved document text. I locate assistant spans by tokenizing successive prefixes of the conversation and taking the difference. A decode-back check asserts that the supervised span contains the reference answer.

The base model is quantized to 4-bit NF4 with double quantization and bf16 compute. LoRA adapters (r = 16, α = 32, dropout 0.05) are attached to the q, k, v, o, gate, up, and down projections, for 29.1M trainable parameters (0.32%). I used AdamW with learning rate 10−4, cosine decay, and 5% warmup, a batch size of 1 with 16 gradient-accumulation steps, and 2 epochs, giving 30 optimizer steps. I did not pack sequences or truncate them.

4.1  Long-context memory

At 22k tokens, two transient tensors dominated peak memory. The first is the logits tensor, whose size is the sequence length L times the vocabulary size V (about 152k); upcast to fp32 for the loss, it occupies roughly 16 GB. I compute the cross-entropy in blocks of 1,024 positions, each under gradient checkpointing, accumulating summed losses and token counts:

ℓ = ( Σb Σt∈b CE(Woutht, yt) ) / |{t : yt ≠ −100}|

The result is identical to the unchunked loss. The second is attention. The model's full-attention layers use a head dimension of 256, for which the installed PyTorch build provides no flash or memory-efficient backward kernel on the training hardware. The scaled-dot-product attention dispatcher silently fell back to the math kernel, which materializes an L×L score matrix (about 18 GB per layer at 22k tokens). I registered a replacement attention implementation that processes query blocks of 1,024 against their causal key prefix, with each block checkpointed so that backward recomputes one score block at a time. Together with layer-level gradient checkpointing, these changes reduced peak memory on the longest example from out-of-memory at 80 GB to about 25 GB. Training loss fell from 5.59 to 2.18 over the 30 steps.

5  Evaluation

5.1  Protocol

Every model receives the same system prompt and tool schemas and is served by vLLM with FP8 weights, greedy decoding, and thinking disabled. In the replayed-evidence condition, the recorded search calls and their responses are inserted into the context, so all models condition on identical retrieved evidence. The model then has up to five further rounds. A calculate call is executed by an evaluator that implements the same grammar as the MCP tool. A repeated search receives a fixed notice that search is unavailable. An LLM grader compares each final answer with the CPA reference using the benchmark's rubric, which assigns a correct or incorrect verdict and a score from 0 to 100. A human reviewer audited the grader's verdicts in depth. Tool use is scored separately, on the model's first call when it is shown only the question and tool schemas.

The fine-tuned model corrects two of the base model's three errors and introduces none. Only the weights differ between the two runs, so the difference is attributable to fine-tuning, but it amounts to two questions. On the first-call tool metrics (whether a tool was called, the correct tool chosen, the arguments valid against the schema, and the folder and tax-year filters correct), the fine-tuned model scored 42/42 on every metric and the base model 41/42. Both models invoked calculate on 1 of the 42 questions. The fine-tuned model's remaining error divides correctly, but uses income tax where the question asks for total tax. This is an operand-selection failure, which arithmetic tooling does not address.

5.5  Effect of tool execution on the measurement

Under an earlier protocol, additional tool calls after the replayed evidence received no response. Under that protocol the two models tied at 38/42. The fine-tuned model's errors were mostly empty answers following tool calls that were never answered. When the calls were executed, those answers became correct. An offline evaluation that does not execute tool calls therefore measures a model that is prevented from carrying out the behavior it was trained to perform. I treat tool execution as a requirement of the evaluation protocol, not an optional detail.

6  Limitations

The held-out set contains 42 questions, and the difference between the matched runs is two of them. I report no confidence intervals or repeated runs. Retrieval is held fixed by design, so these results characterize the generator rather than the end-to-end system. Grading relies on an LLM grader with human review, and the review found at least one reference answer that contradicts its own question. The data come from a single firm and a single tax year. Finally, aggregate accuracy does not show that the model abstains when evidence is insufficient, or that it is robust to misleading retrieved content.

7  Future work

None of the following has been run. I plan to:

  1. measure the rate of answers containing figures that no retrieved evidence supports;
  2. test abstention on questions from which a required component has been removed;
  3. test recovery from tool errors, timeouts, and malformed tool outputs;
  4. test robustness to conflicting or deliberately misleading documents injected into retrieval;
  5. scale the training corpus to 3,000–5,000 synthetic examples, evaluated on a sealed test set that is not examined during development.

All results are from de-identified evaluations on clients excluded from training. No client data appear in this report.
